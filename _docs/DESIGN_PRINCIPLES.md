# Timeline 设计原则 - 快速参考

## 一句话核心

> **Timing 合并的是"人的注意力"，而不是"时间"。**

---

## 三个关键转变

### 1️⃣ 数据流的改变

```
【旧】Activity → 直接渲染 → 用户看到"系统事件"
【新】Activity → Session 聚合 → 用户看到"认知会话"
```

### 2️⃣ 阈值的改变

```
【统计合并】30 分钟（用于 Reports）
【视觉合并】30 秒～90 秒（用于 Timeline）← 我们实现的

这两套系统独立存在，不冲突。
```

### 3️⃣ 评估标准的改变

```
【旧】"Activity 有没有被准确记录？"
【新】"用户能不能一眼看懂这一天？"
```

---

## 两个核心参数

| 参数 | 含义 | 阈值 | 为什么 |
|------|------|------|--------|
| **noiseThreshold** | < 此值的活动 = 噪声 | **30s** | 用户感知不到的短闪 |
| **visualContinuityThreshold** | 两活动间隔 < 此值 + 同项目 = 连续 | **90s** | 用户的"专注中断"感受阈值 |

---

## 四个实现层面（按优先级）

### ① 噪声抑制 ⭐⭐⭐
< 30s 的活动被吸收进相邻 Session，不单独显示。

**效果**：避免"碎片化"

### ② 时间连续性 ⭐⭐⭐
同项目 + 间隔 < 90s → 自动合并，看起来像没被打断。

**效果**：符合用户的"连续工作感"

### ③ 语义连续性 ⭐⭐
同应用 + 间隔 < 90s → 也可以合并（可选）

**效果**：进一步减少视觉噪声

### ④ UI 美化（不是关键）
- 圆角、阴影、动画

**教训**：不做前 3 个，这些只会"让噪声看起来更精致"

---

## 三个不要做的事

❌ **不要直接迁移统计阈值到 Timeline**
- 30 分钟的合并对视觉没用
- 这样 Timeline 看起来仍然会很碎

❌ **不要把 Activity 直接当成 Session**
- Session 是"用户感受到的单位"，不是"系统记录的单位"
- 需要一个中间层（SessionAggregator）

❌ **不要让用户自己"解释"Timeline**
- 不要加 tooltip、help text、onboarding
- 应该是"一眼看懂"的，不需要解释

---

## 验证：5 秒规则

**方法**：
1. 找个不懂代码的人
2. 显示 Timeline 5 秒
3. 问：**"你看到的是我'干了什么'，还是'系统记录了什么'？"**

**预期**：用户说"干了什么"

**如果用户说"系统记录了什么"**：
→ 说明 Session 聚合可能还不够激进，试试降低阈值

---

## 与 Timing 的对标

| 维度 | Timing 做法 | 我们现在做的 |
|------|-----------|-----------|
| 噪声处理 | < 30s 吞掉 | < 30s 吞掉 ✓ |
| 间隔处理 | 同项目 < 90s 合并 | 同项目 < 90s 合并 ✓ |
| 颜色编码 | Project 主色 | 仍用 App 颜色（可升级） |
| 下钻能力 | 可查看细节 | Session 包含 underlyingActivityIds ✓ |

---

## 可以升级的方向（不急）

### Level 1（当前）
- ✅ Session 聚合
- ✅ 噪声抑制
- ✅ 基础合并规则

### Level 2（可选）
- ☐ Project 主色 + App 作为辅助
- ☐ Confidence 编码（饱和度）
- ☐ 噪声可视化（灰色小条）

### Level 3（高级）
- ☐ 点击展开看细节 Activities
- ☐ 时间戳标签
- ☐ Confidence 作为筛选条件

---

## 一句话总结

**你现在的 Timeline 从"系统日志"变成了"用户故事"。**

用户不再问"系统在什么时间干了什么"，而是问"我这一天的故事是什么"——后者是正确的问题。
